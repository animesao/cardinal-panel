# Безопасность cardinal-panel

Панель управляет игровыми серверами и **сама является точкой входа в
инфраструктуру**: через неё создаются контейнеры, выдаются SFTP-доступы и
доступы к базам данных. Поэтому к безопасности здесь отношение строгое.

## Модель безопасности

Панель — серверное приложение (Nuxt 4 / Nitro) с сессиями на основе
NextAuth и API-ключами для внешних клиентов. Основные границы:

1. **Граница ролей.** Роль проверяется по **свежему** значению из базы, а
   не из сессии: JWT-сессия кэширует роль, поэтому понижение должно
   действовать мгновенно. Проверка роли выполняется в обработчике, а не
   только в middleware — одна ошибка в middleware открыла бы все
   админские маршруты.
2. **Граница API-ключей.** Уровни доступа (`1` — чтение, `2` — запись)
   проверяются по маршруту: список разрешённых путей задан в
   `KEY_POLICY`. Управление ключами и настройками через API
   **намеренно невозможно** — только через интерфейс.
3. **Граница узлов.** Панель доверяет только узлу, чей токен совпал с
   сохранённым. Сравнение токенов — постоянного времени.
4. **Граница аутентификации.** Второй фактор обязателен для **всех** способов
   входа, включая OAuth: иначе OAuth-вход обходил бы 2FA.
5. **Граница доверия к прокси.** IP клиента берётся из `X-Forwarded-For`
   только если соединение пришло с адреса из `TRUSTED_PROXY`. Иначе
   троттлинг входа обходился бы одной сменой заголовка.
6. **Граница процесса.** systemd-юнит запускает панель от
   непривилегированного пользователя `cardinal` с песочницей
   (`ProtectSystem=strict`, `NoNewPrivileges`, `PrivateTmp`,
   `ProtectKernelTunables`, `RestrictSUIDSGID`).
7. **Граница тенантов.** Разграничения доступа к серверам нет: панель
   доверяет границе «панель ↔ wings», а wings отвечает за изоляцию
   контейнеров. См. [«Что не является уязвимостью»](#что-не-является-уязвимостью).

## Что защищено и как

| Данные | Хранение | Комментарий |
|---|---|---|
| Пароль пользователя | **scrypt** (N=16384, r=8, p=1, соль 16 байт) | Сравнение через `timingSafeEqual` |
| API-ключ | **только SHA-256** хэш | Секрет показывается один раз при создании |
| Сессии | подписанный JWT | Ключ — `NEXTAUTH_SECRET` |
| OAuth-секреты | **AES-256-GCM** | Ключ — scrypt от `NEXTAUTH_SECRET` |
| Пароли БД пользователей | scrypt | Как у пользователей панели |
| Резервные коды 2FA | **bcrypt** | Одноразовые, горят после использования |
| Токен узла wings | сверка постоянного времени | Сам токен в БД — открытым текстом |

Прочие меры:

- **Лимиты запросов.** Клиентский API — 60/мин на ключ; вход — 10 попыток
  на e-mail за 15 минут и 30 на IP за 10 минут; 2FA — 5 попыток на
  пользователя за 5 минут. Счётчики входа привязаны к идентичности, а не
  к IP.
- **Ограничение размера тела** запроса и разбор multipart без выгрузки
  всего файла в оперативную память.
- **Проверка URL** для обращений к внешним адресам (SSRF): схема, хост,
  запрет внутренних адресов, пининг проверенного адреса на момент
  подключения.
- **Проверка архивов** при импорте: запрет выхода за пределы каталога,
  абсолютных путей и «../», проверка целей символических ссылок.
- **Аудит** действий: включение/выключение сервера, файлы, базы,
  бэкапы, доступы. Пишется в журнал сервера.
- **Журнал входов**: IP, User-Agent, провайдер.

## Что хранится открытым текстом

Честный перечень — эти значения лежат в базе без шифрования:

| Что | Где | Риск |
|---|---|---|
| **Токен узла wings** | `nodes.token` | Утечка базы даёт доступ к узлу |
| **Пароли хостов БД** | `database_hosts.password` | Утечка базы даёт доступ к СУБД |
| **Пароли SFTP** | `sftp_credentials.password` | Утечка базы даёт доступ к файлам серверов |

Для OAuth-секретов в проекте уже есть шифрование (`oauth-seal`,
AES-256-GCM). Перевести на него три перечисленных вида данных — отдельная
задача; пока размещение панели следует считать доверенным, а базу —
чувствительным активом.

**Практический вывод:** резервная копия базы панели — такой же секрет,
как сама панель. Храните её с теми же правами (`0600`) и не выкладывайте
в открытые места.

## Рекомендации по развёртыванию

- **Публикуйте панель по HTTPS** через обратный прокси. OAuth-провайдеры
  без HTTPS не работают, а cookie без `secure` передаются открытым текстом.
- **Держите панель на `127.0.0.1`.** Наружу её выпускает только nginx.
- **Ограничьте `TRUSTED_PROXY`** точным списком адресов прокси. Список
  `*` или `0.0.0.0/0` обесценивает защиту.
- **Смените `NEXTAUTH_SECRET`**, если он когда-либо был в открытом
  доступе. После смены все сессии сбрасываются.
- **Не используйте `NEXTAUTH_URL` и `NUXT_PANEL_URL` с `localhost`** для
  публичной панели — это ломает OAuth-колбэки.
- **Ограничьте доступ к `/etc/cardinal-panel/panel.env`**: права `0600`,
  владелец `cardinal`. В этом файле — все секреты панели.
- **Ограничьте доступ к базе** `/var/lib/cardinal-panel` (права `0750`).
- **Настройте ротацию журналов** — журнал systemd растёт без ограничения:

  ```bash
  sudo journalctl --vacuum-size=200M
  # и в /etc/systemd/journald.conf: SystemMaxUse=200M
  ```
- **Регулярно проверяйте журнал входов** (Account → История входов).
- **Ограничьте доступ к узлам wings** отдельным токеном на каждый узел:
  компрометация одного узла не даёт доступа к остальным.

## Сообщение об уязвимости

Не открывайте публичный issue на уязвимость.

Пришлите письмо на **security@animesao.dev** (или через
[GitHub Security Advisories](https://github.com/animesao/cardinal-panel/security/advisories/new)
с пометкой private) — в описании укажите:

- что и как воспроизвести;
- затронутую версию;
- оценку влияния.

Ответ ожидается в течение 7 дней. Уязвимости подтверждаются и исправляются
до публичного раскрытия; в `CHANGELOG.md` появится запись о выпуске.

Публичное раскрытие — приветствуется, если о проблеме уже сообщили и
уязвимость исправлена.

## Что не является уязвимостью

- **Панель не разделяет доступ между пользователями одного сервера.**
  Проверка «есть ли у пользователя права на сервер» — на уровне wings;
  сама панель отдаёт по `userId` всё, что принадлежит пользователю.
  Если это не устраивает — это вопрос модели доступа, а не уязвимость.
- **Администратор видит всё**, включая SFTP-доступы и базы. Это его роль.
- **Ошибка в консоли сервера** (команда, вывод, содержимое файла) —
  ожидаемое поведение: у пользователя есть доступ к серверу.
- **Панель доверяет wings.** Ответ wings принимается как есть (кроме
  проверки URL). Компрометация wings означает компрометацию всего, что
  под её управлением.
