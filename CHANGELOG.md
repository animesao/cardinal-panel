# Changelog — cardinal-panel

Все значимые изменения панели. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версии — по [SemVer](https://semver.org/lang/ru/).

## [Unreleased]

## [0.4.2] — 2026-10-21

### Fixed

- **Установщик съедал ~300 МБ диска без нужды.** Он ставил npm-зависимости
  «для миграций», хотя миграции SQLite работают на встроенном `node:sqlite`
  и не требуют ни одного npm-пакета. На VPS с маленьким диском это давало
  `ENOSPC` и «database or disk is full» — база не создавалась, панель не
  стартовала. Теперь зависимости не ставятся, а миграция выполняется
  сразу; если всё же не хватило модуля, установщик ставит зависимости и
  повторяет попытку.
- **Свободное место проверяется ДО установки.** Новый шаг `check_disk_space`
  (по умолчанию требуется 256 МБ, ключ `--min-free`) с понятной ошибкой
  вместо падения на середине с `ENOSPC` и сломанным сервисом.
- **Неудачная установка больше не рапортует об успехе.** Если сервис не
  поднялся или панель не отвечает на `/api/health`, в сводке печатается
  «installed, BUT NOT WORKING», выводятся подсказки (`journalctl`, `df`)
  и скрипт завершается с ненулевым кодом.
- **`package-lock.json` добавлен в релизный пакет** — установка
  зависимостей детерминирована (`npm ci`), версии не резолвятся заново.

### Changed

- **`--help` печатает шапку файла, а не строки по номерам.** Номера строк
  разъезжались при каждой правке шапки, и справка обрезалась.

### Tests

- 111 юнит-тестов (было 106): 5 новых — порядок проверки диска, отсутствие
  npm-install без нужды, lock-файл в пакете, ненулевой код при неудаче,
  устойчивая справка.

## [0.4.1] — 2026-10-21

### Fixed

- **Установщик не работал ни на одной машине.** `/etc/os-release` определяет
  переменную `VERSION` (например `24.04.4 LTS (Noble Numbat)`), и её
  подстановка перетирала версию панели: проверка «версия задана?» проходила,
  и установщик пытался скачать
  `releases/download/v24.04.4 LTS (Noble Numbat)/cardinal-panel-24.04.4 LTS (Noble Numbat).tar.gz`
  — curl отвергал такой URL как некорректный, установка падала на первом
  же шаге. Версия панели переименована в `PANEL_VERSION`, а `VERSION` из
  `os-release` сбрасывается сразу после подключения файла.
- **Версия из GitHub API больше не проходит «как попало».** Если API вернёт
  не-SemVer значение, установщик сообщает об этом внятно, а не собирает
  битый URL.

### Tests

- 106 юнит-тестов (было 103): 3 новых — регрессия на коллизию `VERSION`
  с `os-release` (проверяется и `unset VERSION`, и отсутствие обращений к
  `$VERSION` как к версии панели), проверка SemVer и имени архива.

## [0.4.0] — 2026-10-21

### Fixed

- **Вход по e-mail+паролю был невозможен для аккаунтов с паролем.**
  Колбэк `signIn` не различал парольный вход (`provider = 'credentials'`)
  и OAuth: правило «OAuth-вход не должен обходить пароль» применялось и к
  парольному входу, поэтому аккаунт с паролем отклонялся с
  `PasswordAccountRequired`. Под удар попадали ровно те аккаунты, которые
  создаёт оператор — `create-admin`, форма первичной настройки и установщик
  (то есть автоматически созданный администратор не мог войти в панель).
  Правило теперь применяется только к OAuth-провайдерам.
- **Парольный вход с 2FA отклонялся даже с верным кодом.** Проверка
  «2FA обязателен для всех способов входа» стояла и для парольного входа,
  где TOTP уже проверен в `authorize()` — пользователь вводил верный код и
  получал отказ. Теперь проверка 2FA в колбэке касается только OAuth.
- **Парольный вход затирал привязку OAuth-провайдера.** После входа по
  e-mail+паролю в колбэк записывались `provider`/`providerId` от
  credentials-провайдера, что уничтожало привязку аккаунта к Discord или
  GitHub. Теперь привязка обновляется только при OAuth-входе.

### Added

- **Сквозные тесты (Playwright, 8 шт.)** по собранной панели: health,
  редирект на дашборд, форма входа, отказ при неверном пароле, успешный
  вход администратором, передача сессии через API, пустая сессия без
  авторизации, живость панели после внутреннего 404. Тесты поднимают
  production-сборку на временной БД (`scripts/e2e-server.mjs`) и гоняются
  в CI — именно они нашли баг с входом.
- **`scripts/e2e-server.mjs`** — подготовка чистой БД, создание
  администратора и запуск `.output/server/index.mjs` для Playwright.
- **`playwright.config.ts`** и `npm run test:e2e`.

## [0.3.0] — 2026-10-21

### Added

- **Полная установка одной командой.** Установщик доводит панель до
  рабочего состояния: публичный адрес (`--domain`), обратный прокси
  (nginx) с корректными заголовками `X-Forwarded-*`, отключённой
  буферизацией (иначе SSE-события приходят пачками с задержкой в минуту)
  и поддержкой WebSocket, TLS через certbot/Let's Encrypt, первый
  администратор (неинтерактивно, пароль печатается один раз) и узел
  `cardinal-wings` через настоящий API панели.
- **Регистрация узла wings автоматически.** Установщик выпускает
  временный админ-ключ (`scripts/admin-api-key.mjs`), регистрирует узел
  через `POST /api/admin/nodes` — с реальной синхронизацией конфига с
  wings (`POST /v1/config`) — и **сразу отзывает ключ**.
- **`scripts/admin-api-key.mjs`** — выпуск и отзыв API-ключа администратора
  напрямую в БД (тем же приёмом, что `create-admin.mjs`): в БД лежит
  только SHA-256 хэш, сам секрет показывается один раз.
- **`packaging/nginx/cardinal-panel.conf`** — шаблон vhost: заголовки
  прокси, `proxy_buffering off` для SSE, WebSocket через
  `$connection_upgrade`, `client_max_body_size 512M` для бэкапов и
  файлового менеджера.
- **Ключи установщика:** `--domain`, `--admin-email`, `--wings-url`,
  `--wings-token`, `--no-proxy`, `--no-tls`.

### Changed

- **Конфиг перезаписывается, а не сохраняется как есть:** `NEXTAUTH_SECRET`
  сохраняется при переустановке (сессии не разламываются), а публичный
  адрес, порт и режим обновляются. Раньше старый `panel.env` оставался
  целиком, и смена домена молча ломала OAuth-колбэки.
- **`--help` работает без root** — проверка прав перенесена после разбора
  аргументов.

### Fixed

- **`--help` печатал половину справки** (`sed -n '2,30p'` не покрывал
  новые ключи) и требовал root.
- **Секреты не попадают в репозиторий:** добавлена проверка
  `scripts/check-no-secrets.mjs` (в CI) и тест, что установщик не
  пишет `SECRET=` в каталог установки.

### Tests

- 98 юнит-тестов (было 82): 6 на `admin-api-key.mjs` (выпуск ключа,
  хэш в БД, отказ не-админу, отзыв, scopes) и 10 на согласованность
  установщика с шаблонами (все плейсхолдеры подставляются, секреты не
  в репозитории, отзыв ключа идёт после запроса, systemd-юнит берёт
  секреты из отдельного файла).

## [0.2.0] — 2026-10-21

### Added

- **Развёртывание панели на runtime cardinal.** Новый режим установщика
  `--install-mode cardinal`: образ `cardinal-panel:<версия>` собирается из
  релизного пакета через `cardinal build` (одна стадия — сборка `.output`
  уже готова, native-модулей нет, образ переносим между машинами), сервис
  поднимается через `cardinal up` по описанию `/etc/cardinal-panel/cardinal.toml`,
  миграции выполняются внутри контейнера (`cardinal exec`), включается
  boot-восстановление (`cardinal bootstrap --install`) — контейнер переживает
  перезагрузку хоста.
- **`Dockerfile.cardinal`** — образ для runtime cardinal: база `node:24-alpine`,
  непривилегированный пользователь `10001:10001`, `VOLUME /app/data`.
- **`packaging/cardinal/cardinal-panel.toml`** — описание сервиса для cardinal:
  `network_mode = "host"` (панели нужен доступ к wings на `127.0.0.1:8080`
  и SFTP на `:2022`, в мосте эти адреса указывают внутрь контейнера),
  именованный том `panel-data`, `cap_drop = ["ALL"]`, `no_new_privs = true`,
  healthcheck на `/api/health`.
- **Ключи установщика:** `--install-mode <cardinal|systemd>`,
  `--network <host|bridge>`, `--image-tag <тег>`.
- **Тесты развёртывания на cardinal** (8 шт.): compose-файл разбирается и
  содержит только поля, поддерживаемые схемой `cardinal/internal/config`;
  Dockerfile использует только инструкции, поддерживаемые билдером cardinal;
  все `COPY`-источники образа есть в релизном пакете. Схема и список
  инструкций продублированы в тесте намеренно — расхождение должно ломать
  CI панели, а не сборку образа.
- **Проверка TOML и Dockerfile настоящими парсерами cardinal.** Оба файла
  разобраны `cardinal/internal/config` и `cardinal/internal/builder` — схема
  и поддерживаемые инструкции подтверждены на настоящем коде рантайма.

### Fixed

- **`COPY output/` → `COPY .output/`** в `Dockerfile.cardinal`: каталог
  сборки называется `.output` (с точкой), как его кладёт Nitro. Сборка
  образа падала бы с «no such file or directory».

## [0.1.0] — 2026-10-20

### Added

- **Сборка и релиз:** пайплайн `build.yml` (lint → typecheck → тесты →
  сборка → `npm audit` → gitleaks) и `release.yml` (тег `v*` → артефакты
  `.tar.gz` + `.sha256` + SPDX-SBOM → GitHub Release).
- **Установщик** `install.sh`: ставит панель из GitHub Releases, проверяет
  SHA-256, создаёт пользователя и каталоги, генерирует
  `NEXTAUTH_SECRET`, накатывает миграции, включает systemd-юнит.
  Поддержаны `--version`, `--dir`, `--data-dir`, `--port`, `--no-start`,
  `--uninstall`.
- **Docker:** `Dockerfile` (multi-stage, Node 24, non-root, healthcheck) и
  `docker-compose.yml` с именованным томом под SQLite.
- **systemd-юнит** `packaging/systemd/cardinal-panel.service` с
  песочницей (`ProtectSystem=strict`, `NoNewPrivileges`, `PrivateTmp`).
  Секреты вынесены в отдельный `EnvironmentFile` с правами 0600, чтобы не
  светить их в `systemctl show`.
- **Эндпоинт здоровья** `GET /api/health`: версия, uptime и состояние БД.
  Без авторизации, чтобы балансировщик и Docker HEALTHCHECK отличали
  «панель сломалась» от «панель занята».
- **Юнит-тесты** (vitest) для `server/utils`: `clientip`, `password`,
  `pagination`, `ratelimit`, `oauth-seal` — 74 теста.
- **`scripts/sync-version.mjs`**: источник истины — файл `VERSION`,
  синхронизируется с `package.json`; режим `--check` для CI.
- **`scripts/package-release.mjs`**: сборка релизного пакета, контрольные
  суммы и SPDX-SBOM.
- **`scripts/simulate-install.mjs`**: прогон шагов `install.sh` в песочнице
  (распаковка → перенос → миграции → запуск сервера → health). Гоняется в
  CI, чтобы раскладка файлов после установки проверялась до выкладки на
  VPS, а не после.

### Security

- **Критических уязвимостей в production-зависимостях не осталось.**
  `npm audit fix` обновил транзитивные пакеты (`simple-git`,
  `fast-glob`, `globby`, `@nuxt/devtools`): было 4 critical → стало 0.
  Оставшиеся 14 high — исключительно build-инструментарий
  (`tailwindcss`, `chokidar`, `micromatch`, `esbuild`, `postcss`,
  `vite-builder`), в рантайм запросов они не попадают и ломающей
  правки без смены мажорных версий не имеют. Гейт CI —
  `npm audit --audit-level=critical --omit=dev`; полный отчёт
  сохраняется артефактом.

### Fixed

- **IPv6-адреса склеивались в один rate-limit бакет.** `normalizeIp` в
  `server/utils/clientip.ts` отбрасывал «порт» у голого IPv6:
  `fe80::1` нормализовался в `fe80:`, поэтому все адреса с одинаковым
  префиксом делили один счётчик попыток входа. IPv6 в квадратных скобках
  с портом (`[2001:db8::1]:443`) разбирался неверно.
- **Typecheck падал** на опции `cookie` в `nuxt.config.ts`: она осталась
  от API `@sidebase/nuxt-auth` v0 и не поддерживается в v1. Удалена как
  мёртвая конфигурация.
- **Health-эндпоинт проверял БД неверным методом** (`db.execute` есть
  только у mysql2-драйвера, у sqlite-proxy — `db.all`): панель всегда
  отдавала 503. Теперь выбирается метод по диалекту.
